বড় কোম্পানিগুলোও এই ভুলগুলো করেছে। চারটা বাস্তব ঘটনা দেখি।

▶1 ২০১২ সালে Knight Capital নতুন trading code deploy করল। একটা server-এ নতুন code পৌঁছায়নি, সেখানে পুরনো code চালু হয়ে গেল। প্রায় ৪৫ মিনিটে ক্ষতি হলো ৪৪০ মিলিয়ন ডলারেরও বেশি।

▶2 ২০১৭ সালে GitLab-এ একজন engineer ভুল করে primary database-এর ডেটা মুছে ফেললেন। তারপর দেখা গেল, backup-গুলো ঠিকমতো কাজ করছিল না। প্রায় ছয় ঘণ্টার database পরিবর্তন হারিয়ে গেল।

▶3 ২০২৪ সালে CrowdStrike-এর একটা ত্রুটিপূর্ণ update একসাথে অনেক কম্পিউটারে চলে গেল। Microsoft-এর হিসাবে প্রায় ৮৫ লাখ Windows device বন্ধ হয়ে গিয়েছিল।

▶4 আর ২০২৫ সালে Replit-এর AI agent একটা code freeze-এর মধ্যেও একজন user-এর production database মুছে দিয়েছিল। Replit-এর CEO নিজেই বলেছিলেন, এটা কখনো সম্ভব হওয়াই উচিত ছিল না।

প্রতিটার সমাধান আছে। শুধু কোডের আগে design-এ রাখতে হয়।

ভালো খবর হলো—এই বিপদগুলো নতুন নয়। এদের নাম আছে, সমাধানও জানা।

▶1 হঠাৎ traffic বেড়ে যাওয়া। পুরনো ডেটা দেখানো। Cache একসাথে মুছে গিয়ে database-এ ভিড়। একজনের ডেটা আরেকজন দেখে ফেলা। একই পেমেন্টে দুইবার টাকা কাটা।

▶2 ডেটা হারিয়ে যাওয়া। AI agent-এর হাতে master key। API key বা password ফাঁস হওয়া। AI-এর বানানো ভুয়া package install করা। আর এমন deploy, যেটা ভাঙলে ফেরানোর রাস্তা নেই।

▶3 প্রতিটার সমাধান আছে। শুধু কোড লেখার আগে সেটা design-এ রাখতে হয়।

আজকের পুরো আলোচনাটা একটা loop-এ বাঁধা।

▶1 প্রথমে সিদ্ধান্ত নিন। তারপর সেটা লিখে রাখুন। তারপর ছোট ছোট ধাপে বানান।

▶2 প্রতিটা ধাপ test দিয়ে যাচাই করুন। Production-কে পাহারা দিন। আর ভাঙলে দ্রুত ফিরে আসার ব্যবস্থা রাখুন।

▶3 সবচেয়ে গুরুত্বপূর্ণ অংশ: প্রতিটা নতুন ভুল থেকে একটা নতুন rule আর একটা নতুন test। এভাবেই সিস্টেম সময়ের সাথে শক্ত হয়।

ষষ্ঠ নিয়ম access নিয়ে। Replit-এর ঘটনাটা মনে আছে?

▶1 AI agent যদি production database-এর owner credential পায়, তাহলে সে ডেটা পড়তে, বদলাতে, এমনকি মুছেও ফেলতে পারে।

▶2 তাই চাবি আলাদা করুন। Development-এ দরকারমতো access। Production-এ সীমিত, যতটুকু না হলেই নয়। আর backup থাকবে আলাদা account-এ, যেটা app বা agent মুছতে পারবে না।

▶3 আর মুছে ফেলার মতো যেকোনো command—DROP TABLE, rm -rf, database migration—মানুষের approval ছাড়া চলবে না। এটাকে বলে least privilege।

০% AI-এর সুপারিশ করা package ছিলই না। সেই নামে ক্ষতিকর package বানানো যায়: slopsquatting
সূত্র: Spracklen et al., USENIX Security 2025

সপ্তম নিয়ম: দুটো জিনিস চুপচাপ ফাঁস হয়—secret আর dependency।

▶1 API key, password শুধু environment variable-এ রাখুন, git-এ কখনো নয়। Secret scanning চালু রাখুন। আর ফাঁস হলে আগে key বদলান, তারপর অন্য কাজ।

▶2 AI যে package install করতে বলছে, সেটা আসলে আছে কি না, আর কারা বানিয়েছে—দেখে নিন। Lockfile commit করুন। নতুন dependency মানেই review।

▶3 কেন? ২০২৫ সালের একটা গবেষণায় দেখা গেছে, code লেখা AI model-গুলোর সুপারিশ করা package-এর প্রায় ২০ শতাংশ আসলে ছিলই না। হামলাকারীরা ঠিক সেই নামে ক্ষতিকর package বানিয়ে রাখতে পারে। এর নাম slopsquatting।

যে backup কখনো restore করে দেখেননি, সেটা backup নয়—শুধু আশা।

সূত্র: GitLab postmortem, Jan 2017

অষ্টম নিয়ম ডেটা নিয়ে।

▶1 ধরুন, backup হয় প্রতিদিন দুপুর দুটায়। সমস্যা হলো রাত এগারোটায়। মাঝের নয় ঘণ্টার ডেটা কোথায়?

▶2 তাই আগে দুটো সংখ্যা ঠিক করুন। RPO—সর্বোচ্চ কতটুকু ডেটা হারানো মেনে নেবেন। RTO—আবার চালু করতে সর্বোচ্চ কত সময় নেবেন। Point-in-time recovery থাকলে এই ফাঁক অনেক ছোট করা যায়।

▶3 আর GitLab-এর শিক্ষা: যে backup কখনো restore করে দেখেননি, সেটা backup নয়—সেটা শুধু আশা।

▶2 সমাধান idempotency key। প্রতিটা payment attempt-এর জন্য একটা নির্দিষ্ট key। একই key আবার এলে provider নতুন করে টাকা কাটে না।

১০Traffic আর cache

Traffic
  • গড় নয়, সবচেয়ে বেশি ভিড় ধরে capacity

  • Cache কখনো source of truth নয়
  • Stampede ঠেকাতে single-flight
  • ব্যক্তিগত page shared cache-এ নয়

দশম নিয়ম: ভিড় আর cache।

▶1 গড় traffic দেখে capacity ঠিক করবেন না, সবচেয়ে বেশি ভিড়ের দিন ধরে করুন। ঈদের সেলের মতো load দিয়ে আগে test করুন। আর প্রতিটা call-এ timeout রাখুন।

▶2 Cache হলো টেবিলের ওপর রাখা নোট, আসল কাগজ নয়—তাই cache কখনো source of truth নয়। জনপ্রিয় data-র cache একসাথে মুছে গেলে single-flight ব্যবহার করুন। আর কারও ব্যক্তিগত page—ইনভয়স, প্রোফাইল—কখনো shared cache-এ নয়।
